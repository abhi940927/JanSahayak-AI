## 1. Executive Summary

JanSahayak AI previously had placeholder/fallback profile bindings that defaulted unauthenticated or mock sessions to a hardcoded identity (*"Aarav Sharma"*). This implementation completely eliminates all hardcoded user identities across registration, login, dashboards, navigation headers, and database persistence.

Every user—whether registering as a new citizen (e.g., *Abhinav Singh*, *Priya Patel*) or logging in as a field officer, department admin, or super admin—dynamically retrieves and displays their **actual personal data, profile photo, contact details, date of birth, and assigned government clearance** throughout the platform.

All 37 automated test scenarios passed with 0 failures, verified through direct backend test suites and headless Chrome browser automation.

## 3. Registration Implementation

The citizen registration flow (`/register` and `POST /api/auth/register`) strictly validates and captures:

- **Required Fields:**
  - Full Name (minimum 2 characters, trimmed)
  - Email Address (RFC 5322 regex validation, uniqueness verified)
  - Date of Birth (`dob`, calendar picker, rejects future dates)
  - Password (minimum 8 characters, password strength evaluation, confirmation check)
- **Optional Fields:**
  - Mobile Number (E.164 phone formatting)
  - Profile Photo (local device file picker, instant 1:1 circular preview, base64 / Supabase storage upload, max 2MB)

### Security Features:
1. Passwords are never stored in plaintext. They are handled by Supabase Auth (or secure bcrypt hashing in local runtime).
2. The user profile ID strictly matches the UUID generated by Supabase Auth (`auth.users.id`).
3. Citizen role is assigned server-side (`roles: ['citizen']`); client cannot elevate role during signup.

## 4. Login Across All 4 User Roles

The authentication controller (`POST /api/auth/login`) handles all four portal contexts:

1. **Citizen Portal:** Authenticates citizen accounts, populates citizen grievances and personal telemetry.
2. **Government Officer Portal:** Validates field officer credentials and scopes access to the officer's assigned department (e.g., PWD Zone 3).
3. **Department Admin Portal:** Scopes administrative oversight to the designated department (e.g., MCD Municipal Corporation).
4. **Super Admin Portal:** Grants cross-departmental authority, SLA telemetry, and system configuration clearance.

### Multi-Role Support:
For designated accounts holding multiple authorized administrative roles (such as `abhisingh940927@gmail.com` holding both `super_admin` and `department_admin`), login detects `available_roles` and displays a secure role-selection modal, allowing dynamic switching without credential re-entry.

## 7. Row Level Security (RLS) & Anti-Escalation Safeguards

- **Strict Identity Immutability:** `PATCH /api/profile` explicitly rejects any request body attempting to supply `role`, `roles`, `id`, or `email`, returning `HTTP 403 Forbidden`:
  > *"Security violation: User role, identifier and primary email cannot be modified via profile update."*
- **Session Isolation:** Users can only query and modify their own record (`WHERE id = auth.uid()`).
- **Storage Security:** Avatars bucket policies enforce that authenticated users can only write to objects matching their own UUID path (`auth.uid()::text = (storage.foldername(name))[1]`).

---

## 8. Authentication Persistence & Session Lifecycle

- **Browser Refresh:** Sessions persist seamlessly using `localStorage.getItem('jansahayak_token')` and `localStorage.getItem('jansahayak_user')`. On refresh, `loadUserProfile` re-validates the token with `GET /api/profile`.
- **Clean Logout:** Calling `logout()` invalidates the session, purges all local storage keys (`jansahayak_token`, `jansahayak_user`, `jansahayak_role`), and resets state to `null`.
- **Zero Cross-Account Leakage:** Logging into Account B immediately overwrites all in-memory user objects, preventing previous account details from remaining visible.
